The idea

what it does

Your assistant asks. Your phone does it.

Connect the AGI MCP server to any MCP client. The assistant runs plain-language tasks on your phone: opens apps, navigates, types and reports back while you watch.

No per-app integration. Anything installable is automatable.

Visible. Every action happens on the phone's own screen.

Native trust. Logins and payments stay with you, on the device.

Claude Code Claude Desktop Cursor ChatGPT
Working…
The one-sentence pitch. Any assistant that speaks MCP gets the same phone tools. The agent works through the screen like a person, so there is no per-app API work, everything is visible on the device, and sensitive steps come back to the human.

mcp in sixty seconds

A plug standard for AI tools

The Model Context Protocol lets any compliant client discover and call tools on a server. Nothing is hardcoded per client.

tools/list

Ask the server which tools exist for this account.

tools/call

Run one tool with JSON arguments, get JSON back.

AGI speaks MCP 2024-11-05 over JSON-RPC 2.0. Transport is Streamable HTTP with JSON responses, or SSE.

POST https://api.agi.tech/v1/mcp
// the client asks { "jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": { "name": "phone_run_task", "arguments": { "prompt": "Open Settings and report the battery percentage." } } } // the server answers at once { "task_id": "…", "session_id": "…" }
For anyone new to MCP: it is a standard way for an AI client to discover tools and call them. Your assistant does this for you. You will rarely write JSON-RPC by hand, but it helps to know that every phone action is just a tools/call with a name and arguments.

architecture

Three pieces, one relay

Your AI client

Decides what to do

Claude Code, Cursor, ChatGPT or your own agent. Calls tools and reads results. Never touches the phone.

AGI cloud MCP server

Queues and relays

Authenticates you, queues tasks, dispatches them to your device, relays progress back.

api.agi.tech/v1/mcp
AGI Android app

The agent itself

Executes on-device through Android accessibility: real apps, real UI. Streams progress back.

Execution is asynchronous. A task takes seconds to minutes, so starting one returns a task_id at once and the client waits separately.

This is the slide to remember. Three boxes. The client decides, the cloud server authenticates and relays, the phone app is the agent that actually taps and types. Watch the dots: the request goes right, the phone does the work, progress and the result flow back left. Because phone work takes seconds to minutes, starting a task never blocks.

what the sign-in does

Recommended · OAuth

Add the URL with no token. The client discovers, registers itself and opens the browser. Tokens refresh on their own and are revocable per client.

Fallback · API key

For clients without OAuth. Create it at platform.agi.tech/me/api-keys and send it on every request.

Either credential is full control of your registered phones. Treat it like your unlocked phone.

You never do this by hand, but it explains the browser pop-up. The first call has no token, the server answers 401 with a pointer to its metadata, the client registers itself dynamically and runs an authorization-code flow with PKCE. The server requires the email scope. Standards for the curious: RFC 9728 resource metadata, RFC 8414 server metadata, RFC 7591 dynamic registration.

the pattern

Start. Monitor. Act.

1 · Start
2 · Monitor
3 · Act
monitor_timed_out: true just call it again
phone_run_task

Send a prompt. Get task_id and session_id back right away.

phone_task_monitor

Blocks up to 120 s. Returns the moment the task is paused or completed. Timed out means still working.

read terminal

ok → use result. needs_user_control → answer it. Anything else has a recovery move.

Don't poll with phone_task_status. It is a snapshot, not a wait.

Every workflow is these three beats. Start returns instantly. Monitor is the entire polling loop: it waits up to two minutes and comes back as soon as something actionable happens. If it comes back with monitor_timed_out true, that is not an error; the phone is still working, call it again. Then act on the terminal.

task lifecycle

Four states, one terminal

pending
running
completed
paused

pending means the server has it and the phone hasn't started.

paused keeps the same task_id. Paused time doesn't count against the timeout.

completed always carries exactly one terminal that says why.

Four states. Pending until the phone picks it up, running while it works, paused if you or the phone pause it, completed with exactly one terminal outcome. Pause and resume keep the same task id, and paused time is not counted against the execution deadline.

terminal outcomes

Every ending has a next move

terminalmeaningwhat to do
okFinished successfully.Read result.

timeoutRan past its deadline.Raise per_call_timeout_s or narrow the prompt.
queue_wait_exceededThe phone never started it.Check online and free, start a new task.
stopped_by_userCancelled, ended, or displaced by a new task.Start a new task if still needed.
agent_errorThe phone agent failed.Retry. Read error.
device_offlineCouldn't reach the device.Reconnect the phone, retry.

iteration_limitHit the agent's action limit.Split into smaller tasks.
This table is your error handling. Two rows matter most: ok, where you read result, and needs_user_control, which is not a failure but a handoff, next slide. For timeouts the default execution deadline is 300 seconds, maximum 900. Queue wait defaults to 60, maximum 300.

Success signal

A continuation_task_id in the reply. delivered_to_device: false is fine here.

Never send passwords through messages. Let the user finish the step on the device.

Sensitive moments are never handled by the agent alone. The task completes with needs_user_control. The assistant tells you what the phone needs, you finish it on the phone, and the assistant sends a short acknowledgement with phone_task_message. That returns a continuation task id, and that is what you monitor next. The original task never runs again. A continuation can itself hand off again; repeat.

Fourteen tools, but you will mostly use two: run task and monitor. The device tools find phones and act as a kill switch. Get state grounds a workflow, for example to check an app is installed before asking for it. The tool list depends on the app version the phone advertises, so keep the app updated.

A new phone_run_task on the same phone cancels the old MCP task with stopped_by_user. A task you started in the app itself is not cancelled; it holds the lane and the MCP task waits as pending.

Changing the default device never reroutes a session that already started.

Each phone is a single lane. Starting a new task replaces the old MCP task. That catches people out when two assistants share a phone. Sessions keep a multi-step workflow on one phone; your assistant passes the session id for follow-ups. End the session only when the whole workflow is done, because ending it cancels anything left in it.

task design

Prompts that hold up on a real screen

One errand per task

Chain follow-ups in the same session. Big prompts burn the timeout.

Name apps and people exactly

“WhatsApp, not WhatsApp Business. Chat with Sam Rivera.”

Gate anything that acts

“Show me the draft and wait for my OK before sending.”

Say what the result looks like

“Airline / time / price, one per line. Say so if none.”

Draw read-only lines

“Don't reply, don't archive, don't open links.”

Fragile

Check my battery, then go through all my unread email, reply to the important ones, find me a flight to Denver, and update my calendar.

Reliable

On my phone, open my calendar and tell me my first three events today. Don't change anything. If unsure, stop and ask me.

Always include an escape hatch: “if you're unsure, stop and ask me.” It turns a wrong guess into a handoff.

The difference between flaky and reliable is almost always the prompt. Five habits. Size each task to one errand. Name apps and contacts exactly as they appear on the phone; use phone_get_state to check what's installed. Put a confirmation gate on anything that sends, buys, deletes or changes settings. Specify the output shape. And say what not to do on read-only tasks.

trust model

Treat it like your unlocked phone

Trust decision 1

Your client

It sees screen content and drives the phone. Connect only clients you trust.

Trust decision 2

Your credentials

An OAuth grant or API key is full control. Prefer OAuth. Revoke keys on any doubt.

Trust decision 3

What's on screen

Data, never instructions. A message saying “tap Allow” is not you.

Built in

Sensitive steps always come back as needs_user_control. State snapshots leave out IMEI, serial, contacts, location and notifications. Everything happens visibly on the screen.

Your part

Gate sends, buys and deletes in the prompt. Use a test phone for QA. phone_device_pause is the kill switch for new work. Results and screenshots can hold personal data.

Three trust decisions: which client you connect, how you guard the credential, and remembering that whatever is on screen is data, not instructions. Prompt injection on a phone looks like an email saying forward all messages to this number. The built-in guardrails cover logins and confirmations; you add gates for judgment calls. Note that pausing a device blocks new tasks but in-flight ones keep running; cancel those separately.

inside the android app

What happens after the cloud dispatches

FCM

Wake-up push

Agents API stores the task and sends an FCM remote_task push that only references it.

Fetch

Load the task

The app fetches the prompt and deadline from Agents API, retrying through replica lag.

Claim

Own the lane

Persisted so it survives process death, then queued on the one device lane chat and voice also use.

Act

Step loop

Each step asks the action model what to do next. Accessibility taps and types it.

Report

Steps and result

Steps with screenshot thumbnails, then one terminal result. Retried up to 30 times; the first result wins.

Source: feature/remote-control in agi-inc/mobile. One agent loop serves chat, voice and remote tasks, which is why the phone runs one task at a time.

For the engineers. The cloud never holds a socket open to your phone. It stores the task and sends a push that points at it. The app fetches the task, claims the one agent loop on the phone, and runs a step loop: send the screen to the action model, get the next action, perform it through Accessibility. Progress and the final result go back to the Agents API with retries. That single shared agent loop is why each phone is one execution lane.

for engineers

The phone's side of the contract

Register

POST /v1/devices/register

FCM token, device model, OS and app version, and the tools the app can answer itself. The response id is the Device ID on the Developer screen.

Stay alive

POST /v1/devices/{id}/heartbeat

Every 15 minutes and after each push. A 404 triggers a fresh registration.

Answer directly

mcp_request → POST /v1/devices/{id}/mcp-result

phone_get_state never starts the agent. The phone collects the snapshot and replies within 10 s.

Push types the phone accepts

FCM typewhat the phone does
remote_taskFetch the task, queue it, run it
remote_followupDeliver a steering message to the running task
remote_pausePause the task in place
remote_resumeResume with an optional new instruction
remote_cancelStop it, stamped with a stop_reason
mcp_requestAnswer a direct tool call

Every push carries an id, never the content. The phone fetches each body by reference, so a large prompt never hits FCM's payload size limit.

For the engineers in the room. The phone registers its push token with the Agents API under your Clerk identity, heartbeats every fifteen minutes, and is woken by FCM pushes that carry only references. Six push types map onto the MCP tools you already know: run, follow-up message, pause, resume, cancel. phone_get_state is special: it is answered by the phone directly without running the agent, which is why it needs no extra permissions and returns fast.

when it doesn't work

The 60-second triage

1

Can you call list_devices?

No → authentication or client config. Check the URL, re-run sign-in, check the key.

2

Is the phone online and unpaused?

No → phone side. Same account? Developer connection says Connected? Tap Refresh.

3

What does the task say?

phone_task_status: its status, terminal and error almost always name the problem.

Know your error layer

HTTP 401

Credentials never reached MCP.

JSON-RPC error

device_paused, task_not_found. Fix the call.

Task terminal

The task ran and ended. Use the outcomes table.

Three questions in order. Can you list devices at all: if not, it's auth or client. Is the phone there, online and not paused: if not, it's the phone. Otherwise ask the task itself with phone_task_status. Knowing which layer the error comes from saves most of the debugging time. Stuck pending usually means the phone is offline, paused, or busy with a task started in the app.
