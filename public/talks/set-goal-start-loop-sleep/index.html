The problem.

It's not just me. Here's what goes wrong when you look away.

Four ways an agent fails
when you look away.

01

It stops early.

Says "done" when it isn't. (My story.)

02

It cheats.

Makes the check pass instead of the code.

03

It waits for you.

Failure 01

It stops early.

  • By default, the model decides when it's done.
  • Models are optimistic. "Probably done" feels like done.
  • Long, multi-phase work makes it worse: the plan slides out of view.
claudeAll tests pass ✅
mewhich tests did you run?
claudeI didn't run them, but the changes look correct.
  • Nobody wrote down what "done" means, so the model makes it up. That's the root cause.
  • The chat on the right is the generic version every developer has seen.

Failure 02

It cheats.

Not on purpose. A failing test is often easier to change than the code.

// before
expect(total(cart)).toBe(1499)
// after "fixing" it
expect(total(cart)).toBe(1349)   // updated to match output

Also seen: skipping the test, mocking the thing under test, catching and swallowing the error.

  • The agent is rewarded for green. If the test is in reach, the test is a target.
  • Lesson: whoever writes the code must not be the one grading it.

Failure 03

It waits for you.

claude · 11:42 pmI'm about to commit these changes. Should I go ahead?
me · 8:03 amyes

Eight hours of compute, zero minutes of work. The agent was polite. You were asleep.

  • Permission prompts are good when you're watching. They're a wall when you're not.
  • Fix later: answer the questions before you leave.

Failure 04

It breaks things.

The wrong folder

A cleanup command, one directory too high.

The wrong branch

A force push to main at 3am.

The wrong hands

A web page with hidden instructions, and your keys sitting right there.

To run unattended, you turn permission prompts off. Then the machine is the only seatbelt.

  • Third card is prompt injection. An agent that reads the web can read instructions you didn't write.
  • The answer isn't "watch it". It's "give it a machine where mistakes don't matter".

Start Loop.

Stop typing "continue". Let the machine type it.

  • Fixes failure three. Remember: I was the loop. Now we replace me.

My "continue", automated

while :; do cat PROMPT.md | claude ; done
  • Geoffrey Huntley calls it the Ralph loop. Each pass is a fresh agent.
  • The plan lives in a file. Read the plan, do one thing, commit, exit, repeat.
  • A YC hackathon team ran it overnight and woke up to 6 shipped repos.
  • One line of bash is the thing I was doing by hand all afternoon.
  • Huntley: watch the loop, and when it fails, fix the loop so it never fails that way again.

Three ways to wake the agent up.

Wake onHowUse it when
The last turn finished/goalOne task, keep going until done
A timer/loop 30m check the deployNothing to wait on, just re-check
An eventCI finished, PR merged, Slack messageYou're waiting on something real

Rule of thumb: if there's an event, watch the event and keep a slow timer as backup.

  • Events are the grown-up version: don't poll CI every minute, get woken when it finishes.

One iteration.

1Check the finish line
2Make the smallest change that should help
3Verify against the real thing
4Better? commit
Not? discard
5Write one log row

↻ back to 1, until the finish line says yes

  • Step 4: the agent throws away work that didn't help. When did you last delete code that didn't help?

The harness.

Everything we just did has a name.

  • Zoom out. The goal, the check, the loop, the contract: none of that is the model.

What is an agent harness?

Agent = Model + Harness

The model

Reads the context and picks the next action. That's all it does.

The harness

All the code that turns that choice into work. Claude Code, Codex, Cursor and Antigravity are all harnesses.

My "done" problem was never a model problem. It was a harness problem.

  • Same model, different harness, very different agent.
  • Next: eight parts every harness shares. One slide each, with an example.

HARNESS 1 / 8

The loop

  • Sends the context to the model.
  • Runs whatever tools it asks for.
  • Feeds the results back in.
  • Decides when the task is finished.

Example

Claude Code reads a file, runs the tests, sees 3 failures, edits, runs again. Each round trip is one turn of the loop. /goal adds the rule for when to stop.

In my story: I was the loop. Every "continue" was me doing this part by hand.

  • The last bullet is the one that failed me. The loop let the model decide when it was finished.

HARNESS 2 / 8

Tools and sandbox

  • Gives the model a terminal, files, a browser and your apps.
  • Runs every task inside its own isolated computer.
  • Keeps the damage from a bad command inside the box.

Example

A Cursor cloud agent gets its own VM with a desktop and browser. A Claude Code cloud session gets a fresh container with only the repo it needs. Delete everything in there? Nothing you care about is gone.

Fixes failure 04: it breaks things.

  • Tools are what the agent can do. The sandbox is where it's allowed to do it. You need both.

HARNESS 3 / 8

Subagents

  • Take side tasks off the main agent and run them in parallel.
  • Start each one with a fresh context window.
  • Send back only a short summary, so the main context stays clean.

Example

pstack's /how: 2 to 4 cheap explorer agents read different corners of the codebase, then one strong model writes a single explanation. The main agent never sees the 40 files they read.

For a multi-phase build: one subagent per phase, one more to review each phase.

  • A subagent is a helper you send off with a clean head and a short brief, who comes back with a one-page answer.

HARNESS 4 / 8

Context management

  • Decides what the model sees on every turn.
  • Loads skills and files only when the task needs them.
  • Summarizes old history before the context window fills up.

Example

A skill is just a folder with a SKILL.md. The harness shows the model a one-line description, and loads the full file only when the task calls for it. 50 skills cost almost nothing until one is used.

Long multi-phase runs are exactly where the plan drops out of view. Keep it in a file, not in the chat.

  • The model only knows what's in front of it right now. Context management is choosing what's in front of it.

HARNESS 5 / 8

Memory

  • Stores progress notes, git history and skills on disk.
  • Lets a new session read what the last one did.
  • Picks the work up where it stopped.

Example

PLAN.md
- [x] phase 1 · tests pass · a1b2c3
- [x] phase 2 · tests pass · d4e5f6
- [ ] phase 3
- [ ] phase 4

Kill the session at 2am, start a new one: it reads PLAN.md and git log, and carries on at phase 3.

  • Lauren Tan: "your codebase is the ultimate form of memory."
  • The checklist is ticked by the check passing, not by the agent saying so.

HARNESS 6 / 8

Guardrails

  • Hold risky actions (emails, payments, deletes) for your approval.
  • Keep real credentials outside the sandbox.
  • Give a prompt injection no credentials to steal.

Example

Work on a branch, never main. Allow git and npm test, nothing else. The GitHub token lives in a proxy outside the box, so the agent can push a PR but can't read the key.

Freedom inside the box, a locked door at the edge.

  • Guardrails are what make "don't ask me" safe to say. You pre-approve the safe things and fence off the dangerous ones.

HARNESS 7 / 8

Verification

  • Stops a summary that only sounds finished.
  • Runs tests, browser checks or a separate grader first.
  • Lets the agent say done only after those checks pass.

Example

Not "I fixed it". Show me the failing test, then the passing test. Show me the before and after screenshot. pstack's author ranks a verification skill as the single best investment.

Fixes failure 01. This is the part my story was missing.

  • Lauren Tan: "The bottleneck with agents is verification."
  • If you only build one part of the harness yourself, build this one.

HARNESS 8 / 8

Observability

  • Traces every model call and tool call.
  • Spots the agent repeating the same failed edit.
  • Pushes it to try a different approach.

Example

03:12 same fix  18/22 discard
03:14 same fix  18/22 discard
03:16 same fix  18/22 discard
03:18 pivot: new approach
03:19 new fix   22/22 kept

Three identical misses is a signal. A plateau means pivot, not stop.

  • Illustrative log. Without traces, you find out at 8am that it tried the same fix 200 times.

pstack · what is a skill?

A skill is written experience.

  • A folder with one SKILL.md file. Plain Markdown.
  • The description says when to use it. The body says how.
  • The agent sees only the one-line description until it needs the rest.
  • Same format in Claude Code, Cursor, Codex.
---
name: encode-lessons-in-structure
description: Apply when you catch
  yourself writing the same instruction
  a second time. Encode the rule as a
  lint, check, or script instead of
  more text.
---
If the fix is structural, only use the
structural fix. The instruction is the
symptom.
  • This is a real pstack skill, nearly the whole file. 34 words. A skill doesn't have to be long to be useful.
  • Students: if you can write a README, you can write a skill.

pstack · why skills matter

Your agent forgets everything.
Every single morning.

"Agents are like new hires in a constant state of amnesia and idiocy. They're capable yet stupid, and very teachable."Lauren Tan

Every run

The lesson loads again tomorrow. You don't repeat yourself.

Every agent

Ten agents in parallel all know it. No one gets a worse brief.

Every teammate

Commit it to the repo. Your whole team's agents learn it too.

  • A chat correction dies with the chat. A skill lives in the repo.
  • This is why the 10,000 uses a week number matters: one person's lessons, reused by a whole team's agents.

pstack · how skills get better

Every scar becomes a skill.

1The agent fails
2You correct it once
3Write it down: a skill, or better, a check
4Next run, it doesn't happen
5Models improve: delete what they no longer need
"I never set out to build pstack. I just started turning every recurring failure mode into a skill. The agents improved because their instructions carried the scars from previous runs."Lauren Tan
  • Step 5 is the surprising one. pstack's history has passes that cut 600 to 700 lines at a time because newer models stopped needing them.
  • Her rule for when to add one: when the same failure shows up twice.

Back to my story

The skill I should have had.

---
name: no-early-done
description: Apply before you say "done" on any multi-phase task.
---
1. Read PLAN.md. Every phase must be ticked.
2. A phase is ticked only when its tests pass. Paste the output.

pstack · every correction becomes structure

Don't fix it twice.

Every time you correct your agent, ask how to make that correction unnecessary. In order of value:

  1. 1Remove the problem with better architecture or data structures
  2. 2Turn it into a lint rule or a test, so CI catches it
  3. 3Turn it into a skill or a rule
  4. 4Have humans review the code to catch it
  • From Lauren's post in August. Number 4 she marks "ngmi". Not gonna make it.
  • Our LOCK file is rung 2: a check, not a request.

pstack · the autonomous run playbook

Three loop rules worth stealing.

"Might help" gets reverted.

If it didn't move the check, it doesn't ride along.

A plateau is not a stop.

Stuck? Change approach. Don't quit, don't spin.

Never relax the goal.

Moving the finish line to declare victory is losing.

Plus a decision log every iteration, so you audit decisions in the morning, not transcripts.

Sleep.

Where does the loop live when your laptop is closed?

  • Fixes failure four, and lets you actually close the lid.

Your laptop is a bad place for a loop.

It sleeps.

Lid closes, Wi-Fi drops, battery dies at 2am.

It's crowded.

Two agents fight each other (and you) for the same files.

It's yours.

Your keys, your cookies, your bank tab. One bad command reaches all of it.

So move the loop.

To a machine that isn't yours, with only the keys the task needs.
