It stops early.

Done ✅

40% built. Who decided it was done? The model.

  • The model reads the context and picks the next action. That's all it does.

  • My "done" problem was never a model problem. It was a harness problem. Next: eight parts, one slide each.

HARNESS 1 / 8

The loop

My story: I was this loop. Every "continue" was me.

  • The loop sends the context to the model, runs whatever tools it asks for, feeds the results back in, and decides when the task is finished.
  • Example: Claude Code reads a file, runs the tests, sees 3 failures, edits, runs again. Each round trip is one turn. /goal adds the rule for when to stop.
  • The "done?" gate is the part that failed me: the loop let the model decide.

HARNESS 2 / 8

Tools and sandbox

The blast stays in the box. Fixes 04.

  • Tools give the model a terminal, files, a browser and your apps. The sandbox runs every task inside its own isolated computer, so a bad command stays inside.
  • Example: a Cursor cloud agent gets its own VM. A Claude Code cloud session gets a fresh container with only the repo it needs. Delete everything in there? Nothing you care about is gone.

HARNESS 3 / 8

Subagents

Helpers in parallel. The main context stays clean.

  • Subagents take side tasks off the main agent and run them in parallel, each with a fresh context window, and send back only a short summary.
  • Example: pstack's /how sends 2 to 4 cheap explorers into different corners of the codebase, then one strong model writes a single explanation. The main agent never sees the 40 files they read.
  • For a multi-phase build: one subagent per phase, one more to review each phase.

HARNESS 4 / 8

Context management

Load what's needed. Squash what's old. Pin the plan.

  • Context management decides what the model sees on every turn, loads skills and files only when the task needs them, and summarizes old history before the window fills.
  • Example: the harness shows the model a one-line description of each skill and loads the full file only when it's needed. 50 skills cost almost nothing until one is used.
  • Long multi-phase runs are exactly where the plan drops out of view. Keep it in a file, not in the chat.

HARNESS 5 / 8

Memory

The next session reads the file and carries on.

  • Memory stores progress notes, git history and skills on disk, so a new session reads what the last one did and picks up where it stopped.
  • The checklist is ticked by the check passing, not by the agent saying so.
  • Lauren Tan: "your codebase is the ultimate form of memory."

HARNESS 6 / 8

Guardrails

Freedom inside the box. A locked door at the edge.

  • Guardrails hold risky actions like emails, payments and deletes for your approval, keep real credentials outside the sandbox, and give a prompt injection no credentials to steal.
  • Example: work on a branch, never main. Allow git and npm test, nothing else. The GitHub token lives in a proxy outside the box, so the agent can push a PR but can't read the key.
  • Guardrails are what make "don't ask me" safe to say.

HARNESS 7 / 8

Verification

"Done" is earned, not said. Fixes 01. The part my story was missing.

  • Verification stops a summary that only sounds finished. It runs tests, browser checks or a separate grader, and only then lets the agent say done.
  • Not "I fixed it". Show me the failing test, then the passing test. Show me the before and after screenshot.
  • Lauren Tan: "The bottleneck with agents is verification." pstack ranks a verification skill as the single best investment. If you only build one part of the harness, build this one.

HARNESS 8 / 8

Observability

Three identical misses is a signal. A plateau means pivot.

  • Observability traces every model call and tool call, spots the agent repeating the same failed edit, and pushes it to try a different approach.
  • Without traces, you find out at 8am that it tried the same fix 200 times.
