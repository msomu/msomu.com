22:58

Set Goal.

Write the finish line before the first line of code.

  • Act one. Before bed, the only thing you have to do well is write the finish line.

A prompt is a request.
A goal is a finish line.

Prompt

"Fix the login bug."

The agent decides when it's done. It usually decides early.

Goal

"The login test passes, the old error is gone from the logs, nothing else in the suite turns red."

Anyone can check it. Including another machine.

  • A prompt ends when the model feels done. A goal ends when something outside the model says yes.
  • If you can't tell whether it's done, neither can the agent.

A good goal is a yes / no question.

tests green · bug no longer reproduces · all 5 PRs merged · pixel diff is zero

  • pstack calls this a "checkable predicate". Fancy word for: a question with a yes or no answer.
  • Read the examples. Every one of them a script can answer.

Your turn · shout it out

Fix these goals.

"Make the app better"

Home screen loads under 1s on a cold start, measured 5 times

"Work on it for 4 hours"

Time isn't a finish line. You'll get 4 hours of activity.

"Refactor the code"

No file over 300 lines, all tests still pass, no public API changed

  • Give the room 30 seconds per card. Take two or three answers, then reveal.
  • This is the one skill they can use tomorrow, even with zero paid tools.

Every agent now has /goal.

Claude Code

/goal all tests in test/auth pass
      and the lint step is clean

Keeps taking turns until the condition holds. Works headless: claude -p "/goal ..."

Codex

Pause, resume, clear, with a budget. "The evidence decides."

In 2026 the tools converged on the same idea: the goal is the contract.

  • Two different companies, same command, same idea. That's usually a sign the idea is right.
  • Our demo used exactly this: claude -p "/goal node check.mjs prints PASS".

The worker never grades
its own homework.

After every turn, a separate model or script checks the goal.
"Probably done" is not done.

  • In Claude Code's /goal, a fresh model checks the condition after each turn, not the one that did the work.
  • Even better: a script. Scripts don't get tired or optimistic.

check.mjs

Our finish line is a script.

$ node check.mjs
FAIL
- 0/22 tests passing
- TODO stubs left in src/index.js

$ echo "// sneaky" >> tests/index.test.js && node check.mjs
FAIL
- tests/index.test.js was changed. The finish line is not yours to move.

Tests and the checker are hashed in a LOCK file. Editing the test to win counts as losing.

  • Agents under pressure will sometimes "fix" the test instead of the code. So we lock the finish line.
  • The joke line lands well. Pause after it.
23:04

Start Loop.

One change. One check. Keep it or throw it away. Repeat.

  • Act two. A goal on its own does nothing. Something has to keep waking the agent up.

The dumbest loop that works

while :; do cat PROMPT.md | claude ; done
  • Geoffrey Huntley calls it Ralph. Each pass is a fresh agent with a fresh memory.
  • The plan lives in a file on disk. Read the plan, do one thing, commit, exit, repeat.
  • A YC hackathon team ran it overnight and woke up to 6 shipped repos.
  • One line of bash. No framework. The repo's ralph.sh is the same idea with a stop condition.
  • Huntley's other line: "everything is a ralph loop". Watch the loop, and when it fails, fix the loop so it never fails that way again.

Three ways to wake the agent up.

Wake onHowUse it when
The last turn finished/goalOne task, keep going until done
A timer/loop 30m check the deployNothing to wait on, just re-check
An eventCI finished, PR merged, Slack messageYou're waiting on something real

pstack's rule: if there's an event, watch the event and keep a slow timer as backup.

  • Most people only know the first one. Events are the grown-up version: don't poll CI every minute, get woken when it finishes.

One iteration.

1Check the finish line
2Make the smallest change that should help
3Verify against the real thing
4Better? commit
Not? discard
5Write one log row

↻ back to 1, until the finish line says yes

  • This is straight from the pstack overnight guide. Point at step 4: the agent throws away work that didn't help.
  • Ask the room: when did you last delete code that didn't help? Agents should do it every loop.

Steal these

Three loop rules.

"Might help" gets reverted.

If it didn't move the number, it doesn't ride along.

A plateau is not a stop.

Stuck? Change approach. Don't quit, don't spin.

Never relax the goal.

Moving the finish line to declare victory is losing.

  • Third rule is the one that matters most. It's why we have the LOCK file.
  • And the escape hatch: if truly stuck, stop and write up why. Better than 8 hours of creative goal reinterpretation.

23:06

Sleep.

Where does the loop live when your laptop is closed?

  • Act three. You can't sleep if the loop needs your laptop to stay open.

Your laptop is a bad place for a loop.

It sleeps.

Lid closes, Wi-Fi drops, battery dies at 2am.

It's crowded.

Two agents fight each other (and you) for the same files and CPU.

It's yours.

Your SSH keys, your cookies, your bank tab. One bad command reaches all of it.

So move the loop.

To a machine that isn't yours, with only the keys the task needs.

  • Third card is the one students skip. Agents in a loop usually run with permissions turned off. A sandbox becomes your only seatbelt.

Cursor

Cloud agents

  • Every agent gets its own VM: terminal, browser, full desktop.
  • Start it from the editor, your phone, Slack or GitHub.
  • It tests its own work and attaches videos and screenshots to the PR.

30%+

of PRs merged at Cursor are made by agents running on their own in cloud sandboxes
(Cursor, Feb 2026)

  • Formerly "background agents". Now the default way Cursor itself ships.
  • The artifacts bit matters: the agent shows you a video of the feature working instead of telling you it works.

Cursor

Automations

Cloud agents that start on a schedule or an event: a Slack message, a new Linear issue, a merged PR, a PagerDuty alert, a webhook. They keep a memory, so they get better each run.

Every push to main

Security review, high risk findings posted to Slack

Every morning

Find code without tests, open a PR adding them

Bug in Slack

Check duplicates, file it, try a fix, reply in thread

  • These three are real automations Cursor runs on its own codebase.
  • Notice: nobody types a prompt. The event is the prompt.

Claude Code

Cloud sessions + scheduled tasks

Cloud sessions

  • Start from claude.ai/code, the phone app, or claude --cloud
  • Close the laptop. It keeps going and opens a PR.
  • Watches its own PR: fixes CI, answers review comments.

Scheduled tasks

  • A saved prompt + repos + connectors
  • Fires on a schedule, an API call, or a GitHub event
  • "Every night at 2am: pull the top bug from Linear, attempt a fix, open a PR."
  • Fun fact for the room: the research and the demo repo for this talk were built in one of these cloud sessions, from my phone.
  • Scheduled tasks launched as "routines" in April 2026.

Block · open source · beta · July 2026

Buzz: agents as teammates

  • Slack-like, but every agent has its own identity.
  • Bring any agent: Claude Code, Codex, goose.
  • Open source, self-host it.

How Block builds Buzz, in Buzz

  1. A human opens a channel and states the goal
  2. Agents research, build and test in the thread
  3. A different agent reviews the builder
  4. Humans decide scope and what merges
  • Same pattern as this whole talk: human sets the goal, agents loop, a separate checker reviews, human signs off in the morning.
  • The difference: it's a team of agents in a group chat, not one agent in a terminal.

Morning.

You audit decisions, not code.

  • Act four. The part nobody demos: what you do when you wake up.

Back to the four lines

The overnight contract.

1 · Goal

"implement every function in src/index.js on a fresh branch"

2 · Finish line

"done means node check.mjs prints PASS. tests stay untouched"

3 · Permission

"don't ask me before committing"

4 · Escape hatch

"if you're truly stuck, stop, write STUCK.md explaining why"

  • Now the four lines from slide two make sense. Each one removes a reason for the agent to stop and wait for you.
  • Permission line: otherwise it blocks at 11pm asking "can I commit?" and you find that out at 7am.

Earn the sleep first.

  • You've done the task once by hand, or watched an agent do it.
  • The agent has the tools you'd use: tests, logs, screenshots.
  • Every step proves its work and can stop the line.
  • You've read a few runs and turned repeat failures into checks.
"It's not if it gets popped, it's when. And what is the blast radius?"Geoffrey Huntley, on running loops without a sandbox
  • Checklist is from the pstack guide. A loop you don't trust just makes unchecked work faster.
  • Sandbox, only the keys it needs, and a branch, never main.

Read 10 rows, not 8 hours.

  • A decision log: time, decision, reason, evidence, result.
  • A reviewer on a different model reads it and flags what needs your eyes.
  • Our morning.sh: did it pass, did the finish line move, what got committed.
